# 手机消费者洞察系统
# 领域本体与知识图谱详细设计规范 V1.0

**文档类型：** 技术架构与数据建模设计  
**适用范围：** 手机消费者研究、消费者洞察、品牌受众拓展、产品规划  
**核心技术：** Domain Ontology + Knowledge Graph + Evidence Store + Event Store + Insight Store  
**推荐技术栈：** Python、FastAPI、PostgreSQL、pgvector、Neo4j  
**设计原则：** 可扩展、可解释、可追溯、可验证、可治理、查询高效

---

# 1. 项目背景与设计目标

## 1.1 业务背景

本项目旨在构建一套基于多源消费者研究数据的智能洞察系统。

当前主要数据来源为手机购机者线下访谈数据，后续将逐步接入：

- 购机者访谈。
- 手机门店现场体验访谈。
- 体验后购买消费者访谈。
- 体验后未购买消费者访谈。
- 竞品消费者访谈。
- 消费者问卷。
- 手机产品及功能资料。
- 市场研究报告。
- 电商评论、社交媒体等外部市场数据。

系统需要通过领域本体和知识图谱，对消费者、消费者需求、手机产品、产品功能、产品卖点、购买行为和市场环境进行结构化建模。

最终通过对话式交互，支持消费者洞察和产品决策。

## 1.2 核心业务目标

系统需要支持四个主要业务方向。

### 目标 A：消费者群体洞察

回答：

- 某国家、某年龄段消费者有哪些购机需求？
- 不同消费者群体的需求有什么差异？
- 不同群体对手机功能和卖点的关注程度如何？
- 哪些需求是显性需求，哪些是潜在需求？
- 哪些消费者具有品牌潜在转化价值？

### 目标 B：手机产品及卖点洞察

回答：

- 某款手机具备哪些产品功能？
- 产品功能对应哪些消费者需求？
- 哪些卖点能够吸引特定消费者群体？
- 哪些功能具备竞争优势？
- 哪些卖点虽然具备技术优势，但消费者感知较弱？

### 目标 C：购买决策洞察

回答：

- 消费者为什么选择某款手机？
- 哪些因素影响消费者购买决策？
- 消费者为什么放弃某个品牌？
- 门店体验是否改变了消费者的购买选择？
- 不同卖点与购买行为之间存在什么关联？

### 目标 D：下一代产品规划

回答：

- 当前消费者有哪些未满足需求？
- 哪些需求在持续增长？
- 当前产品与竞品分别满足了哪些需求？
- 下一代机型应该优先强化哪些功能？
- 哪些产品能力有机会吸引新的消费者群体？

## 1.3 非功能性目标

| 维度 | 设计要求 |
|---|---|
| 可解释性 | 每条重要结论都能追溯至原始证据 |
| 可扩展性 | 新市场、新产品、新数据源不需要修改核心实体体系 |
| 查询效率 | 常见洞察查询优先控制在 2～4 次数据关联操作 |
| 可治理性 | 实体、关系、需求分类均有统一字典 |
| 可验证性 | 支持人工审核、抽样校验和反例分析 |
| 时间演化 | 支持不同年份、不同市场的知识和洞察变化 |
| 数据隔离 | 消费者匿名标识，控制个人信息访问 |
| 可复用性 | 相同需求、功能和卖点可以跨机型、跨市场复用 |

# 2. 总体建模原则

## 2.1 采用三层数据模型

本项目不采用单一知识图谱承载所有数据的方案。

采用三层知识数据体系。

### 第一层：Domain Ontology & Knowledge Graph

领域本体与核心知识图谱。

负责描述相对稳定的业务世界：

- 有哪些品牌？
- 有哪些手机产品？
- 手机具备哪些功能？
- 产品有哪些卖点？
- 有哪些消费者需求？
- 不同需求与功能之间有什么关联？
- 不同消费者群体有什么特征？

该层不直接承载所有访谈内容、行为记录和洞察结论。

### 第二层：Evidence & Event

证据与事件层。

负责描述现实世界中发生的事实：

- 消费者表达了什么？
- 消费者体验了什么？
- 消费者比较了什么？
- 消费者最终购买了什么？
- 某项需求来自多少条访谈？
- 证据发生于什么时间？

### 第三层：Insight

洞察层。

负责保存经过分析产生的业务结论：

- 某个群体最关注什么？
- 哪些卖点与购买行为存在关联？
- 不同群体的需求差异是什么？
- 哪些产品功能可能存在改进机会？

洞察结果需要保存证据引用、分析方法、统计口径和版本。

## 2.2 实体、属性、关系、事实的划分原则

这是本体设计的第一条强约束。

### 实体 Entity

具有独立业务意义，可以被多个对象引用，或者需要独立维护生命周期的概念。

例如：

- Brand
- Product
- Feature
- SellingPoint
- Need
- Consumer
- Market

### 属性 Attribute

用于描述实体特征、支持筛选和排序的信息。

例如：

- 消费者年龄。
- 消费者收入区间。
- 产品重量。
- 电池容量。
- 价格。
- 产品上市日期。

### 关系 Relationship

描述两个业务实体之间相对稳定的语义关联。

例如：

- Product HAS_FEATURE Feature。
- SellingPoint BASED_ON Feature。
- Feature SUPPORTS Need。

### 事实 Fact / Assertion

描述某个关系在具体时间、来源和上下文下是否成立。

例如：

某位消费者在某次访谈中明确表示自己关注夜景拍摄。

它不仅仅是一条：

Consumer HAS_NEED Need。

还需要包含：

- 消费者 ID。
- 需求 ID。
- 访谈 ID。
- 原始证据 ID。
- 表达时间。
- 表达方式。
- 置信度。
- 是否经过人工审核。

因此，本项目将关系事实单独建模。

## 2.3 节点数量控制原则

不允许因为数据中出现了新的词语，就自动创建一个新的知识图谱节点。

实体创建需要满足至少一个条件：

1. 具备独立业务含义。
2. 需要被多个实体重复引用。
3. 需要独立维护属性或生命周期。
4. 需要参与跨市场、跨机型分析。
5. 需要独立建立分类或关联关系。

否则优先作为属性、标签、别名或证据内容处理。

# 3. 核心本体设计

## 3.1 核心实体体系

建议第一期采用 10 类核心实体，加 1 类受控管理实体。

| 编号 | 实体 | 英文名称 | 是否进入核心图谱 |
|---|---|---|---|
| E01 | 品牌 | Brand | 是 |
| E02 | 手机产品 | Product | 是 |
| E03 | 产品功能 | Feature | 是 |
| E04 | 产品卖点 | SellingPoint | 是 |
| E05 | 消费者 | Consumer | 是 |
| E06 | 消费者群体 | ConsumerSegment | 受控创建 |
| E07 | 消费者需求 | Need | 是 |
| E08 | 使用场景 | UsageScenario | 是 |
| E09 | 市场 | Market | 是 |
| E10 | 购买渠道 | Channel | 是 |
| E11 | 产品功能实现与卖点映射 | 作为关系事实管理 | 不新增独立实体 |

购买行为、门店体验、消费者表达等不作为静态本体实体，而是由事件和事实层管理。

这样能够避免把本来属于动态过程的对象全部塞进静态知识图谱。

## 3.2 E01：Brand 品牌实体

### 定义

手机品牌及其品牌体系。

### 属性定义

| 属性 | 类型 | 必填 | 说明 |
|---|---|---|---|
| brand_id | String | 是 | 唯一标识 |
| name | String | 是 | 标准名称 |
| name_localized | JSON | 否 | 多语言名称 |
| aliases | Array | 否 | 品牌别名 |
| country_of_origin | String | 否 | 品牌来源国家 |
| description | Text | 否 | 品牌简介 |
| status | Enum | 是 | active/inactive |
| created_at | Datetime | 是 | 创建时间 |
| updated_at | Datetime | 是 | 更新时间 |

### 唯一性规则

brand_id 全局唯一。

品牌名称需要结合别名表进行消歧。

### 关系

- Brand OWNS Product。

### 设计说明

品牌实体不应承担消费者品牌认知、品牌偏好等动态属性。

例如：

消费者是否认可某品牌、是否愿意购买某品牌，应当进入消费者事实或事件层。

---

## 3.3 E02：Product 手机产品实体

### 定义

代表具体手机机型。

需要注意，手机机型和具体销售 SKU 不是同一个概念。

例如：

某机型有：

- 8GB + 256GB。
- 12GB + 256GB。
- 12GB + 512GB。

如果这些版本的主要功能一致，可以使用同一个 Product，配置作为产品属性或关联配置记录。

如果硬件能力、功能或市场销售版本存在实质差异，则需要区分产品变体。

第一期建议先使用机型级 Product，配置通过 JSONB 保存。

### 属性定义

| 属性 | 类型 | 必填 | 说明 |
|---|---|---|---|
| product_id | String | 是 | 唯一标识 |
| brand_id | String | 是 | 品牌标识 |
| model_name | String | 是 | 机型名称 |
| model_code | String | 否 | 内部型号 |
| product_series | String | 否 | 产品系列 |
| product_category | Enum | 是 | entry/mid/high/flagship |
| launch_date | Date | 否 | 上市日期 |
| target_price_min | Decimal | 否 | 建议价格下限 |
| target_price_max | Decimal | 否 | 建议价格上限 |
| specifications | JSONB | 否 | 产品配置 |
| market_availability | Array | 否 | 销售市场 |
| status | Enum | 是 | 状态 |

### 产品配置示例

```json
{
  "display": {
    "size_inch": 6.7,
    "refresh_rate_hz": 120,
    "resolution": "FHD+"
  },
  "battery": {
    "capacity_mah": 6000,
    "charging_watt": 80
  },
  "camera": {
    "main_mp": 50,
    "ois": true
  },
  "memory": {
    "ram_gb": 12,
    "storage_gb": 256
  }
}
```

### 设计原则

配置参数不需要全部创建 Feature 节点。

例如：

- 电池容量 6000mAh：产品属性。
- 大容量电池：功能概念或标准功能标签。
- 全天候长续航：消费者价值卖点。

只有需要参与跨产品需求关联、统计或推理的功能概念才进入 Feature 实体。

### 关系

- Brand OWNS Product。
- Product HAS_FEATURE Feature。
- Product PROMOTES SellingPoint。
- Product TARGETS ConsumerSegment。

最后一条关系代表品牌或产品的目标受众定位，不能直接当作真实消费者购买事实。

## 3.4 E03：Feature 产品功能实体

### 定义

Feature 描述手机具备的客观技术能力或产品功能。

它回答：

手机能够做什么？

### 功能分类

建议建立一级分类：

| 分类编码 | 分类 | 示例 |
|---|---|---|
| IMAGING | 影像 | 夜景、人像、光学防抖 |
| PERFORMANCE | 性能 | CPU、GPU、散热 |
| BATTERY | 续航 | 大容量电池、快充 |
| DISPLAY | 屏幕 | 高刷新率、高亮度 |
| DESIGN | 设计 | 轻薄、防水、材质 |
| AI | 人工智能 | AI 修图、AI 助手 |
| SYSTEM | 系统 | 系统流畅性、系统更新 |
| AUDIO | 音频 | 立体声、降噪 |
| CONNECTIVITY | 通信 | 5G、Wi-Fi |
| SECURITY | 安全 | 指纹、人脸识别 |

### 属性定义

| 属性 | 类型 | 必填 | 说明 |
|---|---|---|---|
| feature_id | String | 是 | 唯一标识 |
| name | String | 是 | 标准名称 |
| category | Enum | 是 | 功能分类 |
| parent_feature_id | String | 否 | 父功能 |
| description | Text | 是 | 功能定义 |
| aliases | Array | 否 | 别名 |
| standardization_status | Enum | 是 | pending/approved |
| status | Enum | 是 | 状态 |

### 功能层级设计

例如：

```text
影像能力
├── 夜景拍摄
│   ├── 夜景降噪
│   ├── 夜景曝光控制
│   └── 夜景人像
├── 人像拍摄
│   ├── 背景虚化
│   └── 人像肤色优化
└── 视频拍摄
    ├── 视频防抖
    └── 视频夜景
```

使用 parent_feature_id 建立分类树。

不建议把每个技术参数都创建为 Feature。

### 重要区别

Feature 描述产品能力，不代表消费者一定知道、关注或认可这项能力。

例如：

某机型具备 OIS，不代表消费者明确知道 OIS 的含义。

因此：

Product HAS_FEATURE Feature 是产品事实。

Consumer RECOGNIZES SellingPoint 是消费者认知事实。

两者不能混用。

## 3.5 E04：SellingPoint 产品卖点实体

### 定义

SellingPoint 是产品功能面向消费者传递的价值主张。

它回答：

产品希望让消费者感知到什么价值？

### 卖点分类

| 分类 | 示例 |
|---|---|
| IMAGE_VALUE | 专业影像体验 |
| BATTERY_VALUE | 全天候长续航 |
| PERFORMANCE_VALUE | 游戏更流畅 |
| DESIGN_VALUE | 轻薄时尚 |
| DISPLAY_VALUE | 沉浸式视觉体验 |
| AI_VALUE | 智能 AI 创作 |
| SECURITY_VALUE | 更安全的隐私保护 |

### 属性定义

| 属性 | 类型 | 必填 | 说明 |
|---|---|---|---|
| selling_point_id | String | 是 | 唯一标识 |
| name | String | 是 | 标准卖点 |
| category | Enum | 是 | 卖点分类 |
| description | Text | 是 | 卖点语义 |
| value_proposition | Text | 否 | 用户价值表达 |
| target_context | JSONB | 否 | 目标市场、群体、场景 |
| aliases | Array | 否 | 卖点别名 |
| status | Enum | 是 | 状态 |

### 卖点与功能的区别

例如：

| Feature | SellingPoint |
|---|---|
| 6000mAh 电池 | 全天候长续航 |
| 80W 快充 | 快速补能 |
| 光学防抖 | 夜景拍摄更稳定 |
| 120Hz 屏幕 | 操作更流畅 |

同一个 Feature 可以支撑多个 SellingPoint。

同一个 SellingPoint 也可以由多个 Feature 共同支撑。

所以两者是多对多关系。

### 本地化处理

同一个标准卖点在不同国家可能有不同营销表达。

例如：

标准卖点：

LONG_BATTERY_LIFE

菲律宾市场表达：

- Battery that lasts all day.
- Less charging, more freedom.

中国市场表达：

- 全天候长续航。
- 告别电量焦虑。

这些表达不需要创建新的 SellingPoint 节点。

建议通过 `selling_point_localization` 业务表管理：

```json
{
  "selling_point_id": "SP_001",
  "market_id": "MKT_PH",
  "language": "en-PH",
  "localized_name": "Battery that lasts all day",
  "copy_type": "MARKETING_COPY"
}
```

## 3.6 E05：Consumer 消费者实体

### 定义

代表实际参与访谈、体验或购买行为的匿名消费者。

Consumer 是系统中的个体级分析主体。

### 属性定义

| 属性 | 类型 | 必填 | 说明 |
|---|---|---|---|
| consumer_id | String | 是 | 匿名唯一标识 |
| age | Integer | 否 | 访谈时年龄 |
| gender | Enum | 否 | male/female/unknown |
| occupation | String | 否 | 职业 |
| income_range | String | 否 | 收入区间 |
| education | String | 否 | 教育水平 |
| country_code | String | 是 | 国家代码 |
| city_code | String | 否 | 城市代码 |
| purchase_budget_min | Decimal | 否 | 购机预算下限 |
| purchase_budget_max | Decimal | 否 | 购机预算上限 |
| current_phone_brand_id | String | 否 | 当前手机品牌 |
| current_phone_model | String | 否 | 当前手机机型 |
| profile_completeness | Decimal | 是 | 画像完整度 |
| created_at | Datetime | 是 | 创建时间 |

### 重要设计原则

消费者属性必须具有时间语义。

例如：

2026 年 5 月访谈时，消费者年龄为 28 岁。

2027 年 5 月再次访谈时，年龄可能已经变化。

因此需要明确：

- `age_at_interview`
- `profile_observed_at`

不要简单地把消费者年龄当作永久不变属性。

如果消费者在多次访谈中出现，建议使用 Consumer 主表保存稳定身份标识，使用 ConsumerProfileSnapshot 保存每次访谈时的画像快照。

### 隐私要求

- 不保存不必要的姓名、手机号、身份证等直接身份信息。
- 使用匿名 ID。
- 原始访谈文件与消费者主数据分离存储。
- 证据访问应具备权限控制。
- 公开洞察默认只输出聚合结果。

## 3.7 E06：ConsumerSegment 消费者群体实体

### 定义

ConsumerSegment 描述具有明确业务含义、可重复识别和分析的消费者群体。

这是连接消费者与产品卖点的重要分析维度。

### 需要特别区分两种群体

**第一种：动态筛选群体。**

例如：

菲律宾 26～30 岁消费者。

这种群体不需要创建图谱节点。

通过 Consumer 属性和事件数据动态筛选即可。

**第二种：业务定义群体。**

例如：

- 年轻职场人群。
- 游戏重度用户。
- 影像创作爱好者。
- 高端手机潜在换机群体。

这些群体有独立的业务定义，需要跨报告、跨项目复用，可以创建 ConsumerSegment。

### 属性定义

| 属性 | 类型 | 必填 | 说明 |
|---|---|---|---|
| segment_id | String | 是 | 唯一标识 |
| name | String | 是 | 群体名称 |
| description | Text | 是 | 群体定义 |
| segment_type | Enum | 是 | DEMOGRAPHIC/BEHAVIORAL/NEED_BASED/VALUE_BASED |
| definition_rule | JSONB | 是 | 机器可执行的群体条件 |
| definition_version | String | 是 | 定义版本 |
| market_scope | Array | 否 | 适用市场 |
| status | Enum | 是 | 状态 |
| created_at | Datetime | 是 | 创建时间 |

### 群体定义示例

```json
{
  "segment_id": "SEG_GAMER_001",
  "name": "重度游戏用户",
  "segment_type": "BEHAVIORAL",
  "definition_rule": {
    "usage_scenarios": ["MOBILE_GAMING"],
    "gaming_frequency": {
      "operator": ">=",
      "value": 5,
      "unit": "days_per_week"
    }
  },
  "definition_version": "1.0"
}
```

注意：上面的字段只有在原始信源实际采集了游戏频率时才可用于筛选。

不能根据消费者年龄、职业等属性推测其属于重度游戏用户。

### 消费者与群体的关系

Consumer BELONGS_TO ConsumerSegment 可以建立。

但这条关系应当由规则计算、人工审核或模型分类产生，并保存对应的判定依据。

---

## 3.8 E07：Need 消费者需求实体

### 定义

Need 是消费者洞察体系最核心的语义实体之一。

用于统一消费者表达的购买诉求、使用痛点、期望价值和未满足需求。

### 需求分类

建议采用三级分类体系。

**一级：需求领域**

- IMAGE：影像。
- BATTERY：续航。
- PERFORMANCE：性能。
- DISPLAY：屏幕。
- DESIGN：外观设计。
- PRICE：价格。
- SYSTEM：系统体验。
- AI：人工智能。
- SECURITY：安全。
- DURABILITY：耐用性。

**二级：需求主题**

例如：

IMAGE：

- NIGHT_PHOTOGRAPHY。
- SELFIE_QUALITY。
- PORTRAIT_QUALITY。
- VIDEO_STABILITY。

BATTERY：

- LONG_BATTERY_LIFE。
- FAST_CHARGING。
- BATTERY_HEALTH。

**三级：具体需求**

例如：

- 希望夜间拍摄人像清晰。
- 希望长时间游戏不发热。
- 希望外出一天不需要充电。
- 希望自拍时肤色更加自然。

### 属性定义

| 属性 | 类型 | 必填 | 说明 |
|---|---|---|---|
| need_id | String | 是 | 唯一标识 |
| name | String | 是 | 标准需求名称 |
| category | String | 是 | 一级分类 |
| parent_need_id | String | 否 | 父级需求 |
| level | Integer | 是 | 1/2/3 |
| description | Text | 是 | 标准语义定义 |
| need_type | Enum | 是 | PAIN/EXPECTATION/GOAL/REQUIREMENT |
| aliases | Array | 否 | 同义表达 |
| status | Enum | 是 | 状态 |

### 需求的进一步细分

为了让系统具备更强的洞察能力，建议将以下内容作为需求事实的属性，而不是继续创建实体：

- 需求强度。
- 需求优先级。
- 需求紧迫性。
- 是否主动提及。
- 是否为明确购买条件。
- 是否属于未满足需求。
- 是否愿意为此支付额外费用。

这些属性由消费者证据或分析结果支撑。

### 需求分类示例

```text
NEED_ROOT
├── IMAGE
│   ├── NIGHT_PHOTOGRAPHY
│   │   ├── 夜间人像清晰
│   │   └── 夜间照片噪点低
│   └── SELFIE_QUALITY
│       ├── 自拍肤色自然
│       └── 自拍细节清晰
├── BATTERY
│   ├── LONG_BATTERY_LIFE
│   │   └── 外出一天无需充电
│   └── FAST_CHARGING
│       └── 短时间快速补电
└── PERFORMANCE
    ├── GAMING_PERFORMANCE
    └── THERMAL_CONTROL
```

### 特别要求

Need 必须具备标准化治理机制。

例如：

消费者表达：

- Battery lasts long.
- I don't want to charge frequently.
- My battery runs out too quickly.

不能简单地根据关键词将它们全部合并。

需要区分：

- 希望续航时间更长。
- 不希望频繁充电。
- 当前电池续航不满足需求。

它们可能属于同一个需求主题，但表达方向和需求类型不同。

## 3.9 E08：UsageScenario 使用场景实体

### 定义

描述消费者在什么环境或情境下使用手机。

### 分类

| 一级分类 | 示例 |
|---|---|
| WORK | 工作 |
| ENTERTAINMENT | 娱乐 |
| COMMUNICATION | 通信 |
| CREATION | 内容创作 |
| TRAVEL | 出行 |
| SOCIAL | 社交 |
| STUDY | 学习 |
| DAILY_LIFE | 日常生活 |

### 属性

| 属性 | 类型 | 说明 |
|---|---|---|
| scenario_id | String | 唯一标识 |
| name | String | 标准名称 |
| category | String | 分类 |
| parent_scenario_id | String | 父场景 |
| description | Text | 场景说明 |
| aliases | Array | 同义词 |

例如：

```text
ENTERTAINMENT
├── MOBILE_GAMING
│   ├── COMPETITIVE_GAMING
│   └── CASUAL_GAMING
├── VIDEO_WATCHING
└── MUSIC_LISTENING
```

例如：

夜间拍摄是使用场景，夜间拍摄清晰度是消费者需求。

## 3.10 E09：Market 市场实体

### 定义

描述消费者研究发生的国家、地区及市场环境。

### 属性

| 属性 | 类型 | 说明 |
|---|---|---|
| market_id | String | 唯一标识 |
| market_code | String | ISO 国家代码或内部区域代码 |
| name | String | 标准名称 |
| market_type | Enum | COUNTRY/REGION |
| parent_market_id | String | 上级市场 |
| currency | String | 币种 |
| languages | Array | 语言 |
| status | Enum | 状态 |

例如：

```text
GLOBAL
├── SOUTHEAST_ASIA
│   ├── PH
│   ├── ID
│   ├── TH
│   └── VN
└── EAST_ASIA
    ├── CN
    ├── JP
    └── KR
```

第一期可以只创建国家级 Market。

城市级信息如果只是筛选条件，可以放在消费者画像属性中。

只有未来需要独立进行城市市场分析时，才增加城市级市场实体。

### 市场维度注意事项

菲律宾市场和菲律宾消费者不能简单等同。

市场代表分析上下文，消费者代表真实访谈主体。

同一个消费者可能在不同市场生活、工作或购买手机。

应当分别记录居住地、访谈地点、购买地点等字段，不要用一个 country 属性替代全部含义。

# 4. 核心关系本体设计

## 4.1 关系定义规范

所有关系必须明确：

1. 关系唯一编码。
2. 起点实体类型。
3. 终点实体类型。
4. 关系方向。
5. 关系语义。
6. 关系基数。
7. 是否允许反向查询。
8. 是否需要证据支持。
9. 是否属于静态关系。
10. 是否允许直接进入核心图谱。

## 4.2 第一版关系定义

| 编号 | 关系 | 起点 | 终点 | 语义 |
|---|---|---|---|---|
| R01 | OWNS | Brand | Product | 品牌拥有产品 |
| R02 | HAS_FEATURE | Product | Feature | 产品具备功能 |
| R03 | PROMOTES | Product | SellingPoint | 产品主推卖点 |
| R04 | BASED_ON | SellingPoint | Feature | 卖点由功能支撑 |
| R05 | SUPPORTS | Feature | Need | 功能具备满足需求的能力 |
| R06 | APPEALS_TO | SellingPoint | ConsumerSegment | 卖点对群体具有吸引力 |
| R07 | BELONGS_TO | Consumer | ConsumerSegment | 消费者属于群体 |
| R08 | HAS_NEED | Consumer | Need | 消费者表达需求 |
| R09 | USES | Consumer | Product | 消费者使用产品 |
| R10 | LOCATED_IN | Consumer | Market | 消费者居住或所属市场 |
| R11 | USES_IN | Consumer | UsageScenario | 消费者在某场景使用手机 |
| R12 | OCCURS_IN | Need | UsageScenario | 需求发生的场景 |
| R13 | TARGETS | Product | ConsumerSegment | 产品目标群体 |
| R14 | THROUGH | PurchaseEvent | Channel | 购买通过某渠道发生 |
| R15 | OCCURS_IN | PurchaseEvent | Market | 购买发生于某市场 |
| R16 | SELECTS | PurchaseEvent | Product | 购买事件选择的产品 |
| R17 | CONSIDERS | PurchaseEvent | Product | 购买决策中考虑的产品 |
| R18 | INFLUENCED_BY | PurchaseEvent | SellingPoint | 购买行为受到卖点影响 |

说明：

R14～R18 主要属于事件图谱或事实层的关系，不建议全部作为静态知识图谱的永久边。

另外，ConsumerSegment 与 SellingPoint 之间的 APPEALS_TO 关系属于分析性结论，必须带有适用市场、时间、证据和分析方法，不能仅凭产品营销定位自动建立。

## 4.3 关系分级

建议将关系划分为三个等级。

### Level 1：静态语义关系

包括：

- OWNS。
- HAS_FEATURE。
- PROMOTES。
- BASED_ON。
- SUPPORTS。
- OCCURS_IN（需求与场景）。

这些关系主要来自产品资料、技术规格或经过审核的领域知识。

### Level 2：消费者事实关系

包括：

- HAS_NEED。
- USES。
- LOCATED_IN。
- USES_IN。
- BELONGS_TO。

这些关系由消费者档案、访谈、观察和其他数据源产生。

必须保留事实来源。

### Level 3：分析推断关系

包括：

- APPEALS_TO。
- INFLUENCED_BY。
- TARGETS。

这些关系必须明确区分：

- 品牌宣称。
- 消费者直接表达。
- 统计关联。
- 模型推断。
- 实验验证。

不能把模型推断直接转化成确定事实。

# 5. 关键数据模型：Assertion、Evidence、Event、Insight

这一部分是整个架构实现可解释性的核心。

## 5.1 Relationship Assertion 关系事实模型

### 为什么需要 Assertion？

传统图谱：

```text
Consumer --HAS_NEED--> Need
```

这种表达缺少：

- 谁提供了这个事实？
- 什么时间发现的？
- 是消费者直接说的还是模型推断的？
- 原始证据是什么？
- 是否经过人工审核？
- 这个事实是否还有效？

因此需要独立的关系事实表。

### Assertion 数据结构

```json
{
  "assertion_id": "ASR_000001",
  "subject_type": "Consumer",
  "subject_id": "CON_000001",
  "predicate": "HAS_NEED",
  "object_type": "Need",
  "object_id": "NEED_NIGHT_PHOTO",
  "assertion_type": "DIRECT_STATEMENT",
  "source_id": "SRC_000001",
  "evidence_id": "EVD_000001",
  "event_id": "EVT_000001",
  "confidence": 0.96,
  "valid_from": "2026-05-20",
  "valid_to": null,
  "review_status": "APPROVED",
  "created_at": "2026-05-20T10:00:00Z"
}
```

### 字段定义

| 字段 | 类型 | 说明 |
|---|---|---|
| assertion_id | String | 唯一标识 |
| subject_type | String | 主体类型 |
| subject_id | String | 主体 ID |
| predicate | String | 关系类型 |
| object_type | String | 客体类型 |
| object_id | String | 客体 ID |
| assertion_type | Enum | 事实类型 |
| source_id | String | 来源 |
| evidence_id | String | 证据 |
| event_id | String | 关联事件 |
| confidence | Decimal | 抽取置信度 |
| valid_from | Datetime | 事实有效开始时间 |
| valid_to | Datetime | 事实有效结束时间 |
| review_status | Enum | 审核状态 |
| created_at | Datetime | 记录时间 |

### assertion_type 枚举

```text
DIRECT_STATEMENT
OBSERVED_BEHAVIOR
DOCUMENTED_FACT
STATISTICAL_ASSOCIATION
EXPERIMENTAL_EVIDENCE
MODEL_INFERENCE
MANUAL_ANNOTATION
```

注意：

confidence 仅表示抽取或判断置信度。

不能使用 confidence 代替统计显著性、样本代表性或证据强度。

## 5.2 Evidence 证据模型

### 定义

Evidence 是支持、反驳或补充某个业务事实的原始材料或结构化记录。

证据可能来自：

- 访谈原文。
- 访谈员观察。
- 问卷回答。
- 现场行为。
- 产品资料。
- 外部市场报告。

### Evidence 表结构

| 字段 | 类型 | 说明 |
|---|---|---|
| evidence_id | String | 唯一标识 |
| source_id | String | 来源 ID |
| interview_id | String | 访谈 ID |
| consumer_id | String | 消费者 ID |
| evidence_type | Enum | DIRECT_QUOTE/OBSERVATION/SURVEY/REPORT |
| original_text | Text | 原始文本 |
| normalized_text | Text | 标准化文本 |
| language | String | 语言 |
| file_uri | String | 原始文件地址 |
| page_number | Integer | 页码 |
| start_offset | Integer | 原文起始位置 |
| end_offset | Integer | 原文结束位置 |
| speaker | String | 说话人 |
| event_time | Datetime | 事件时间 |
| extraction_confidence | Decimal | 抽取置信度 |
| verification_status | Enum | 验证状态 |
| created_at | Datetime | 创建时间 |

### 证据必须保留原始内容

例如：

Original Text：

"I need a phone with a good camera because I often take photos at night."

Normalized Text：

"消费者希望获得更好的夜间拍摄体验。"

Standard Entity：

NEED_NIGHT_PHOTO。

不能只保存标准化后的需求，而丢失原始表达。

## 5.3 Event 事件模型

### 定义

Event 表示现实中发生的行为或业务活动。

与 Evidence 不同：

- Event 描述发生了什么。
- Evidence 描述我们如何知道发生了什么。

例如：

消费者购买了某款手机，是一个事件。

访谈原文说消费者购买了该手机，是支持该事件的证据。

### 事件类型

```text
INTERVIEW
STORE_VISIT
PRODUCT_EXPERIENCE
PRODUCT_COMPARISON
PURCHASE
PURCHASE_REJECTION
BRAND_SWITCH
PRODUCT_USAGE
PRODUCT_REVIEW
```

### Event 表结构

| 字段 | 类型 | 说明 |
|---|---|---|
| event_id | String | 唯一标识 |
| event_type | Enum | 事件类型 |
| event_time | Datetime | 发生时间 |
| market_id | String | 市场 |
| consumer_id | String | 消费者 |
| product_id | String | 相关产品 |
| channel_id | String | 渠道 |
| event_attributes | JSONB | 事件补充属性 |
| source_id | String | 来源 |
| verification_status | Enum | 验证状态 |
| created_at | Datetime | 创建时间 |

对于涉及多个产品、多个消费者的复杂事件，使用 `event_participant` 和 `event_entity_link` 关联表，不要无限增加 Event 的固定字段。

### 体验后购买事件

例如：

```json
{
  "event_id": "EVT_001",
  "event_type": "PURCHASE",
  "event_time": "2026-05-20T14:30:00Z",
  "market_id": "MKT_PH",
  "consumer_id": "CON_001",
  "product_id": "PROD_001",
  "channel_id": "CHANNEL_STORE",
  "event_attributes": {
    "previous_brand": "BRAND_A",
    "considered_products": ["PROD_002"],
    "experience_before_purchase": true,
    "purchase_budget": 450
  }
}
```

这类事件模型可以自然扩展到未来的门店体验数据。

## 5.4 Insight 洞察模型

### 定义

Insight 是通过证据、统计或分析推导出的业务结论。

它不是原始知识，不应直接混入静态本体。

### Insight 表结构

| 字段 | 类型 | 说明 |
|---|---|---|
| insight_id | String | 唯一标识 |
| title | String | 洞察标题 |
| content | Text | 洞察内容 |
| insight_type | Enum | 洞察类型 |
| market_id | String | 适用市场 |
| segment_definition | JSONB | 群体条件 |
| time_window | JSONB | 时间范围 |
| methodology | String | 分析方法 |
| sample_size | Integer | 样本量 |
| confidence | Decimal | 模型判断置信度 |
| evidence_strength | Enum | 证据强度 |
| status | Enum | 状态 |
| version | Integer | 版本 |
| created_at | Datetime | 创建时间 |
| valid_from | Datetime | 有效开始 |
| valid_to | Datetime | 有效结束 |

### 洞察类型

```text
CONSUMER_PROFILE
NEED_DISTRIBUTION
SELLING_POINT_PREFERENCE
PURCHASE_DRIVER
BRAND_PREFERENCE
COMPETITIVE_ANALYSIS
UNMET_NEED
PRODUCT_OPPORTUNITY
MARKET_TREND
```

### 洞察与证据的关联

单独设计：

`insight_evidence`

字段：

- insight_id。
- evidence_id。
- contribution_type。
- contribution_weight。
- explanation。

contribution_type：

```text
SUPPORT
CONTRADICT
SUPPLEMENT
CONTEXT
```

这样能够支持：

一个洞察由多个证据支撑。

一个证据也可以被多个洞察引用。

# 6. 统一实体 ID 与跨存储关联规范

这是整个系统必须统一的基础设施。

## 6.1 ID 规范

建议：

```text
BRAND_000001
PROD_000001
FEAT_000001
SP_000001
CON_000001
SEG_000001
NEED_000001
SCN_000001
MKT_000001
CHN_000001

SRC_000001
INT_000001
EVD_000001
ASR_000001
EVT_000001
INS_000001
```

ID 生成建议采用 UUID/ULID 或数据库生成机制，外部使用可读前缀作为业务标识。

不要依赖数据库自增 ID 作为跨存储唯一标识。

## 6.2 Entity Registry

建议增加一个统一的实体注册表。

表名：

`entity_registry`

字段：

| 字段 | 说明 |
|---|---|
| entity_id | 全局实体 ID |
| entity_type | 实体类型 |
| canonical_name | 标准名称 |
| status | 实体状态 |
| ontology_version | 所属本体版本 |
| source_system | 首次来源 |
| created_at | 创建时间 |
| updated_at | 更新时间 |

作用：

1. 确保 PostgreSQL 与 Neo4j 使用同一个实体 ID。
2. 防止不同信源创建重复实体。
3. 支持跨数据库关联。
4. 支持实体合并和别名管理。
5. 支持实体版本与状态治理。

## 6.3 Entity Alias

单独维护实体别名表：

`entity_alias`

例如：

| entity_id | alias | language | market |
|---|---|---|---|
| FEAT_001 | OIS | en | GLOBAL |
| FEAT_001 | Optical Image Stabilization | en | GLOBAL |
| FEAT_001 | 光学防抖 | zh | CN |
| FEAT_002 | Fast Charging | en | GLOBAL |
| FEAT_002 | 快充 | zh | CN |

别名不是新实体。

同义词映射必须经过标准化审核，避免语义相近但实际不同的概念被错误合并。

# 7. 图数据库 Schema 设计

## 7.1 Neo4j 节点结构

建议只将核心业务实体投影到 Neo4j。

节点 Label：

```text
Brand
Product
Feature
SellingPoint
Consumer
ConsumerSegment
Need
UsageScenario
Market
Channel
```

节点公共属性：

```text
entity_id
name
status
ontology_version
created_at
updated_at
```

不建议将所有证据、访谈段落和洞察结论都创建为图节点。

这些数据由 PostgreSQL 保存。

## 7.2 核心关系

```cypher
(:Brand)-[:OWNS]->(:Product)

(:Product)-[:HAS_FEATURE]->(:Feature)

(:Product)-[:PROMOTES]->(:SellingPoint)

(:SellingPoint)-[:BASED_ON]->(:Feature)

(:Feature)-[:SUPPORTS]->(:Need)

(:Consumer)-[:BELONGS_TO]->(:ConsumerSegment)

(:Consumer)-[:HAS_NEED]->(:Need)

(:Consumer)-[:USES]->(:Product)

(:Consumer)-[:LOCATED_IN]->(:Market)

(:Consumer)-[:USES_IN]->(:UsageScenario)

(:Need)-[:OCCURS_IN]->(:UsageScenario)

(:Product)-[:TARGETS]->(:ConsumerSegment)
```

注意：HAS_NEED、BELONGS_TO、TARGETS 等事实性或推断性关系，如果进入 Neo4j，必须是从已审核 Assertion 投影出来的结果。

不能直接将模型抽取结果全部写入图谱。

## 7.3 图数据库索引

```cypher

FOR (n:Brand)
REQUIRE n.entity_id IS UNIQUE;

CREATE CONSTRAINT product_id_unique

REQUIRE n.entity_id IS UNIQUE;
```

## 7.4 图谱边属性

对于进入图数据库的动态关系，建议采用：

```text

```

# 9. 消费者群体动态查询设计

这是系统后续能否支持灵活提问的关键。

## 9.1 为什么不能预创建所有群体节点？

假设有：

- 10 个国家。
- 10 个年龄段。
- 2 种性别。
- 5 个收入区间。
- 8 种需求类型。
- 10 种场景。

如果把这些维度全部组合成 ConsumerSegment，群体数量会迅速膨胀。

而且新的业务问题可能随时出现。

因此：

**群体条件由查询时动态组合，只有稳定且具有业务价值的群体才创建 ConsumerSegment。**

## 9.2 Segment Query DSL

建议定义标准群体查询 DSL。

```json
{
  "segment_query": {
    "market": "PH",
    "age": {
      "gte": 26,
      "lte": 30
    },
    "gender": null,
    "income_range": null,
    "purchase_status": "PURCHASED",
    "purchase_period": {
      "start": "2026-01-01",
      "end": "2026-12-31"
    }
  }
}
```

注意：

这里的市场、年龄和购机时间分别有不同语义。

market 应指定居住市场、访谈市场或购买市场之一。

age 应明确为访谈时年龄或购买时年龄。

purchase_period 则使用真实购买事件时间。

不能把它们统一处理为 Consumer.country、Consumer.age 和 Interview.date。

## 9.3 群体筛选流程

```text
自然语言
   ↓
解析市场、年龄、时间等条件
   ↓
校验条件定义
   ↓
ConsumerProfileSnapshot 筛选
   ↓
Purchase Event 关联
   ↓
形成 Consumer ID 集合
   ↓
后续需求、卖点和证据统计
```

建议群体筛选优先使用 PostgreSQL。

Neo4j 不负责大规模人口属性过滤。

## 9.4 群体定义版本

对于长期使用的业务群体，必须保存：

- 群体定义。
- 定义版本。
- 创建时间。
- 适用市场。
- 计算规则。
- 样本范围。

同名群体的定义发生变化时，不应覆盖旧定义。

# 10. 产品功能、卖点、需求之间的关联模型

这是手机消费者洞察区别于普通知识图谱的重要部分。

不能简单使用：

Feature SUPPORTS Need。

因为它只能描述功能与需求之间的理论匹配。

需要增加不同层次的关系语义。

## 10.1 三种核心关联

### A. 技术能力关联

```text
Feature SUPPORTS Need
```

示例：

大容量电池 → 满足长续航需求。

来源：

- 产品技术资料。
- 产品测试。
- 领域知识。

### B. 消费者感知关联

```text
SellingPoint APPEALS_TO ConsumerSegment
```

示例：

全天候长续航 → 对长时间户外工作人群具有吸引力。

来源：

- 消费者访谈。
- 消费者评价。
- 问卷调查。

### C. 购买决策关联

```text
PurchaseEvent INFLUENCED_BY SellingPoint
```

示例：

消费者表示因为续航表现最终选择某机型。

来源：

- 消费者直接表达。
- 购买过程观察。
- 行为记录。
- 实验研究。

三种关联不能互相替代。

## 10.2 需求满足度模型

建议增加一个独立的分析事实：

`need_satisfaction_fact`

用于分析某款产品对某种需求的满足程度。

字段：

```text
product_id
need_id
market_id
segment_definition
satisfaction_level
measurement_method
sample_size
evidence_ids
valid_from
valid_to
```

satisfaction_level 可以采用：

```text
VERY_LOW
LOW
MEDIUM
HIGH
VERY_HIGH
UNKNOWN
```

必须明确：

这是消费者感知满足程度，不一定是客观技术性能。

例如：

产品客观续航时间较长，不代表消费者一定认为续航满意。

这两个指标应分别记录。

## 10.3 卖点吸引力模型

建议将以下指标放在统计事实层，而不是作为 SellingPoint 节点的永久属性：

| 指标 | 定义 |
|---|---|
| Awareness Rate | 消费者认知比例 |
| Mention Rate | 访谈中主动提及比例 |
| Interest Rate | 表达兴趣比例 |
| Purchase Association | 与购买行为关联比例 |
| Conversion Rate | 体验或营销后实际转化比例 |
| Willingness To Pay | 支付意愿 |
| Satisfaction | 使用后的满意程度 |

每个指标必须定义分母、分子、统计时间和样本来源。

尤其是 Mention Rate：

不能把主动提及和被访谈员提示后提及混为一谈。

## 11.4 实体消歧机制

建议采用四级流程：

1. 精确 ID 匹配。
2. 标准名称匹配。
3. 别名词典匹配。
4. 语义相似度 + LLM 判断。

无法确定时：

- 不自动创建正式实体。
- 进入 Pending Entity。
- 保存原始表达。
- 由人工审核或批量消歧。

尤其是需求实体，必须避免因语言差异而重复创建。

例如：

"Long battery life"、"All-day battery"、"Battery lasts longer"。

可能属于同一需求主题，但是否属于同一三级需求，需要根据上下文判断。

## 11.5 人工审核策略

建议采用风险分级。

| 类型 | 处理方式 |
|---|---|
| 明确产品型号 | 可自动映射，抽样审核 |
| 标准功能名称 | 可自动映射 |
| 消费者明确需求 | 自动抽取，必要时审核 |
| 隐含需求 | 必须保留推断标识 |
| 购买原因 | 需要证据核对 |
| 因果关系 | 不允许仅凭 LLM 自动认定 |
| 新需求实体 | 进入待审核队列 |

# 13. 端到端示例：菲律宾消费者购机需求分析

## 13.1 用户问题

2026 年菲律宾 26～30 岁消费者在购机方面有哪些诉求，哪些手机卖点能够推动他们购买？

## 13.2 问题拆解

```text
T1：筛选菲律宾市场消费者。

T2：筛选 26～30 岁消费者。

T3：关联 2026 年实际购机事件。

T4：抽取并统计消费者需求。

T5：关联需求与产品功能。

T6：关联产品功能与卖点。

T7：分析消费者直接表达的购买原因。

T8：寻找支持证据和反例。

T9：形成群体洞察。
```

## 13.3 查询逻辑

第一步：PostgreSQL 筛选消费者。

```sql
SELECT DISTINCT c.consumer_id
FROM consumer c
JOIN consumer_profile_snapshot p
    ON p.consumer_id = c.consumer_id
JOIN event e
    ON e.consumer_id = c.consumer_id
WHERE p.age BETWEEN 26 AND 30
  AND e.event_type = 'PURCHASE'
  AND e.market_id = 'MKT_PH'
  AND e.event_time >= '2026-01-01'
  AND e.event_time < '2027-01-01';
```

注意：这里假设画像快照中的年龄是购机时年龄。如果年龄来自访谈时点，需要另外计算或使用明确的访谈时间口径。

第二步：统计需求。

```sql
SELECT
    a.object_id AS need_id,
    COUNT(DISTINCT a.subject_id) AS consumer_count,
    COUNT(*) AS assertion_count
FROM relationship_assertion a
JOIN consumer_profile_snapshot p
    ON p.consumer_id = a.subject_id
WHERE a.predicate = 'HAS_NEED'
  AND a.review_status = 'APPROVED'
  AND p.age BETWEEN 26 AND 30
GROUP BY a.object_id
ORDER BY consumer_count DESC;
```

实际生产查询还需要通过符合条件的购买事件和对应访谈时间限定消费者集合，避免将其他年份或其他购买行为的需求错误计入。

第三步：查询需求对应功能和卖点。

```cypher
MATCH (sp:SellingPoint)-[:BASED_ON]->(f:Feature)
      -[:SUPPORTS]->(n:Need)
WHERE n.entity_id IN $need_ids
RETURN
    n.entity_id,
    n.name,
    f.entity_id,
    f.name,
    sp.entity_id,
    sp.name;
```

第四步：回溯证据。

通过 Assertion 查询：

```sql
SELECT
    a.assertion_id,
    a.subject_id,
    a.object_id,
    e.original_text,
    e.source_id,
    e.event_time
FROM relationship_assertion a
JOIN evidence e
    ON e.evidence_id = a.evidence_id
WHERE a.predicate = 'HAS_NEED'
  AND a.review_status = 'APPROVED'
  AND a.object_id = ANY(:need_ids);
```

第五步：分析购买驱动。

只统计消费者明确表达的购买原因，另外单独统计观察行为和模型推断。

不得将所有提及卖点的消费者都算作被该卖点驱动购买。

## 13.4 结果输出

最终报告应该包含：

1. 样本范围与样本量。
2. 消费者需求排名。
3. 需求提及率。
4. 卖点认知与兴趣情况。
5. 购买原因及其证据强度。
6. 不同消费者群体的差异。
7. 典型消费者原话。
8. 反例与未满足需求。
9. 结论适用范围。
10. 下一代产品机会。

如果没有足够证据证明某卖点推动购买，应该明确标记为待验证，而不是让 LLM 补全结论。

# 14. 时间、版本与冲突管理

## 14.1 双时间模型

建议重要事实采用双时间管理：

- Valid Time：现实事实发生或有效的时间。
- Transaction Time：系统记录或修订该事实的时间。

例如：

某消费者在 2026 年 5 月表达续航需求，系统在 2026 年 6 月才导入数据。

这两个时间不能混淆。

## 14.2 本体版本

建议采用语义版本：

```text
MAJOR.MINOR.PATCH
```

例如：

```text
1.0.0
1.1.0
2.0.0
```

- MAJOR：实体语义、关系语义或核心结构发生不兼容变化。
- MINOR：新增实体、属性、关系或分类。
- PATCH：修复定义、别名和描述。

每条实体、Assertion 和洞察都需要记录 ontology_version。

## 14.3 实体合并

例如：

原始数据产生了：

```text
NEED_001：夜间拍照清晰
NEED_002：夜景拍摄效果好
```

人工确认它们属于同一标准需求后：

- 保留一个主实体。
- 另一个标记为 MERGED。
- 建立旧 ID 到新 ID 的映射。
- 更新别名表。
- 保留历史 Assertion 和 Evidence。
- 不直接物理删除历史数据。

## 14.4 需求冲突

不同消费者存在相反诉求时，不应当将其视为实体冲突。

例如：

- 消费者 A 希望更轻薄。
- 消费者 B 希望更大电池，可以接受更重的手机。

这两条事实都成立。

应该通过群体分析识别需求差异，而不是合并或覆盖。

# 15. 查询性能与图谱规模治理

## 15.1 查询职责分工

| 任务 | PostgreSQL | Neo4j | pgvector |
|---|---|---|---|
| 消费者属性筛选 | 主 | 不负责 | 不负责 |
| 群体动态生成 | 主 | 不负责 | 不负责 |
| 需求数量统计 | 主 | 辅助 | 不负责 |
| 产品功能关联 | 辅助 | 主 | 不负责 |
| 功能与需求路径 | 辅助 | 主 | 不负责 |
| 访谈原文召回 | 辅助 | 不负责 | 主 |
| 证据来源查询 | 主 | 不负责 | 辅助 |
| 洞察统计 | 主 | 辅助 | 不负责 |

## 15.2 核心性能优化策略

### 第一：实体过滤前置

先通过 SQL 得到消费者集合，再做图查询。

不要先在图中遍历全部消费者，然后过滤年龄和市场。

### 第二：图查询模板化

针对常见查询建立固定 Cypher 模板。

不允许 LLM 随意组合关系路径。

### 第三：需求与功能关系预计算

对高频需求和功能关联建立可复用结果。

### 第四：统计结果物化

对以下指标可以建立物化视图：

- 各市场需求提及率。
- 各年龄段需求分布。
- 各机型功能覆盖情况。
- 卖点认知率。
- 购买驱动因素分布。

必须保存统计口径和更新时间。

### 第五：缓存

缓存 Key 应包含：

```text
query_type
market
time_range
segment_definition_hash
ontology_version
data_version
```

本体或数据更新时，应能使相关缓存失效。

## 15.3 第一阶段性能验收目标

以下为建议的工程目标，不是未经测试的性能承诺。

| 指标 | 第一阶段目标 |
|---|---|
| 常见群体筛选 | P95 ≤ 500ms |
| 常见图关系查询 | P95 ≤ 500ms |
| 标准统计查询 | P95 ≤ 2s |
| 证据检索 | P95 ≤ 2s |
| 完整洞察查询 | P95 ≤ 10s（不含复杂长文本生成） |
| 图谱最大默认遍历深度 | 4 |
| 查询最大返回数量 | 可配置 |
| 证据回溯率 | 100%（已发布洞察） |

最终需要基于真实数据量和硬件进行 Benchmark。

# 16. 本体治理与数据质量

## 16.1 实体生命周期

建议：

```text
PENDING
   ↓
APPROVED
   ↓
ACTIVE
   ↓
DEPRECATED
   ↓
MERGED / ARCHIVED
```

新发现的需求和功能不能直接进入正式本体。

必须先进行语义审核。

## 16.2 关系生命周期

```text
EXTRACTED
   ↓
VALIDATED
   ↓
APPROVED
   ↓
ACTIVE
   ↓
EXPIRED / REVOKED
```

不同类型的关系可以采用不同审核策略。

## 16.3 质量指标

| 指标 | 定义 |
|---|---|
| Entity Precision | 实体识别准确率 |
| Entity Recall | 实体识别召回率 |
| Entity Resolution Accuracy | 实体消歧准确率 |
| Relation Precision | 关系抽取准确率 |
| Need Mapping Accuracy | 需求标准化准确率 |
| Evidence Traceability | 证据可追溯率 |
| Ontology Coverage | 本体覆盖率 |
| Duplicate Entity Rate | 重复实体比例 |
| Unsupported Assertion Rate | 缺乏证据支持的关系比例 |

第一期建议重点验收：

- Need Mapping Accuracy。
- Relation Precision。
- Entity Resolution Accuracy。
- Evidence Traceability。

这些指标比单纯统计图谱节点数量更有价值。

# 19. 最终架构决策总结

本项目的核心设计决策如下。

| 设计领域 | 最终决策 |
|---|---|
| 本体范围 | 10 类核心实体 + 受控消费者群体 |
| 消费者群体 | 动态筛选为主，稳定业务群体为辅 |
| 产品功能 | 独立 Feature 实体 |
| 产品卖点 | 独立 SellingPoint 实体 |
| 消费者需求 | 独立 Need 实体，三级分类 |
| 消费者行为 | Event 事件模型 |
| 关系可信度 | Assertion 关系事实模型 |
| 原始依据 | Evidence 独立存储 |
| 洞察结果 | Insight 独立存储 |
| 统一标识 | Entity Registry |
| 图数据库 | Neo4j |
| 业务数据库 | PostgreSQL |
| 语义检索 | pgvector |
| 查询方式 | LLM + DSL + SQL/Cypher |
| 推理方式 | 受控关系查询 + 统计分析 + 证据论证 |
| 时间管理 | Valid Time + Transaction Time |
| 知识治理 | 本体版本、实体审核、关系审核 |

## 19.1 最重要的架构原则

最终需要形成这样的知识体系：

```text
                   DOMAIN ONTOLOGY
                         │
              ┌──────────┴──────────┐
              │                     │
          PRODUCT                CONSUMER
              │                     │
       ┌──────┼──────┐         ┌────┼────┐
       │      │      │         │    │    │
     Feature SellingPoint     Need Scenario Segment
       │      │                │
       └──────┴────────────────┘
                    │
             RELATIONSHIP
                ASSERTION
                    │
             ┌──────┴──────┐
             │             │
          EVIDENCE        EVENT
             │             │
             └──────┬──────┘
                    │
                 INSIGHT
                    │
             PRODUCT DECISION
```

这里需要特别强调：

本体负责定义概念，图谱负责表达关系，Assertion 负责表达有依据的事实，Evidence 负责提供证据，Event 负责描述业务活动，Insight 负责保存分析结论。

六者职责明确，互相引用，但不相互替代。

## 19.2 第一阶段最终交付目标

第一期不以图谱节点数量、关系数量作为验收标准。

而是以一个真实业务问题能否完成完整分析闭环作为标准：

**给定一批菲律宾手机购机者访谈数据，系统能够识别消费者画像，统一需求分类，建立消费者与需求、产品功能和卖点之间的关联，统计不同消费者群体的需求差异，并对每条重要洞察提供可回溯、可验证的证据。**

这才是本体建模与知识图谱建设真正需要达到的目标。
